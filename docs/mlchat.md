# MLChat: подключение к backend

Пакет `gis-assistant-mlchat`, Python 3.12: русский запрос → интерпретация/уточнение →
проверенный native `FilterV1`. Сервер, сессии, авторизация, LLM-транспорт, SQL и карта
принадлежат существующим backend/frontend.

Основание: требования v0.4, Спецификация v0.3 и ЧТЗ v1.3 из задания 21.10.2026.
Между листами смещены номера REQ, поэтому трассировка ниже использует FR/UC.

## Совместимость и сборка

Рабочие типы импортируются из установленного `gis-assistant-backend==0.1.0`;
исходники backend в модуль не копируются. Эталон зафиксирован в
`mlchat/backend-reference.json`:

- SHA-256 ZIP: `b6860f90057a450665039feb8fd1043106f91952884b20a973e985c5a67f0aa7`;
- SHA-256 wheel: `83672bbb603be2816715e2299d54a955b7a8c66811bcb708ceac112db4b13060`;
- контрольные суммы файлов импортируемых контрактов.

Получить wheel от владельца backend. Если его нет, сборщик ниже использует
предоставленный неизменённый ZIP: проверяет SHA-256, собирает пакет во временном
каталоге и сохраняет результат в локальную `.artifacts/backend/`.

Из корня репозитория в PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install 'build>=1.2,<2' 'hatchling>=1.27,<2'
# Пропустить сборщик, если wheel уже предоставлен владельцем backend.
.\.venv\Scripts\python.exe -X utf8 scripts/build_mlchat_backend_reference.py 'C:\Users\artur\Downloads\backend-main.zip'
Get-FileHash .artifacts/backend/gis_assistant_backend-0.1.0-py3-none-any.whl -Algorithm SHA256
.\.venv\Scripts\python.exe -m pip install .artifacts/backend/gis_assistant_backend-0.1.0-py3-none-any.whl
.\.venv\Scripts\python.exe -m build --wheel --no-isolation
```

Одинаковая версия backend с другими контрактами не считается проверенной.
При обновлении backend проверить интерфейс и регрессию, затем обновить эталон.
Архив backend и исходники серверного приложения не изменяются.

Для сборки из исходного архива можно использовать `python -m build --sdist --no-isolation`.
В него входят `mlchat/`, метаданные проекта, эта инструкция, профили Qwen 14B/9B
и сборщик совместимого backend. Тестовые и экспериментальные материалы не входят.

## Подключение в серверном окружении

Передать владельцу backend `dist/gis_assistant_mlchat-0.1.3-py3-none-any.whl`,
эту инструкцию и профиль модели, если используется рекомендуемый вариант.
В окружении с совместимым backend:

```powershell
python -m pip install gis_assistant_mlchat-0.1.3-py3-none-any.whl
$env:DIALOGUE_FACTORY = 'mlchat.integration:create_dialogue'
$env:LLM_BASE_URL = 'http://localhost:11434'
$env:LLM_MODEL = 'mlchat-qwen14b'
$env:LLM_RESPONSE_MODE = 'json_schema'
```

Перезапустить backend штатным способом. Адрес Ollama должен быть доступен из процесса
backend: localhost в контейнере относится к самому контейнеру. Backend добавляет
`/v1` и использует `/chat/completions`. MLChat не создаёт собственный HTTP-клиент
и не выбирает, не скачивает и не запускает модель.

Ключи и пароли передаются через серверное окружение и не сохраняются в Git.
`json_schema` ограничивает ответ производной схемой; затем MLChat проверяет
семантику и capabilities. `json_object` гарантирует только JSON и недостаточен
для соблюдения контракта. Скрытого отката между режимами нет.

## Профиль модели

Ранее проверен профиль на базе `qwen2.5:14b-instruct-q3_K_M`.
На машине с Ollama, где исходная модель уже скачана:

```powershell
ollama create mlchat-qwen14b -f config/ollama/Modelfile.qwen14b
```

Профиль задаёт контекст 4096 и максимум 512 токенов ответа. Для длинных сообщений
и большого каталога этого контекста может быть недостаточно.

Температура 0 в Modelfile не гарантирует температуру 0 в HTTP-запросе:
штатный LLMClient не передаёт `temperature`, а проверенные версии совместимого API
Ollama 0.30.10/0.40.7 подставляют 1.0. У фабрики create_dialogue сохранено прежнее
поведение. Для отдельного профиля 9B ниже предусмотрена явная передача параметров
через существующий клиент без изменения исходников backend.

С прежним промптом на Ollama 0.40.7 профиль прошёл 31/32 сценария, медиана 5,2 с,
максимум 23,5 с. Оставшийся сбой — сценарий отказа на AVG.
Это результаты интерпретатора, не гарантия качества или времени полного приложения.

## Профиль Qwen3.5 9B

Добавлен в MLChat 0.1.2. Используется уже установленная qwen3.5:9b Q4_K_M.
Создание отдельного имени модели не скачивает новые веса и не меняет исходный тег:

```powershell
ollama create mlchat-qwen35-9b -f config/ollama/Modelfile.qwen35-9b
```

| Настройка | Значение | Где применяется |
| --- | --- | --- |
| Контекст | 8192 токена вместо 32768 | Modelfile: num_ctx |
| Максимальный ответ | 512 токенов | Modelfile: num_predict |
| Температура | 0 | Modelfile и HTTP-запрос |
| top_p | 0.8 | Modelfile и HTTP-запрос |
| top_k | 20 | Modelfile |
| min_p | 0 | Modelfile |
| repeat_penalty | 1, без штрафа | Modelfile |
| presence_penalty / frequency_penalty | 0 / 0 | Modelfile |
| Рассуждения | Отключены | HTTP-запрос: reasoning_effort="none" |

Контекст 8192 выбран как ограничение памяти с запасом относительно профиля 14B:
помимо запроса передаются схема, capabilities и история уточнения. Поддержка всех
сообщений на предельном лимите 8000 символов и состояний предельного размера
не подтверждена. Лимит 512 может оказаться недостаточным для большого числа условий;
обрезанный ответ остаётся технической ошибкой и не передаётся на поиск.

Штрафы повторения отключены, поскольку ключи JSON и названия полей закономерно
повторяются. Новая конфигурация отличается от предыдущего быстрого прогона 9B,
где контекст был 32768 и presence_penalty=1.5; старые 27/32 не являются её оценкой.

Чтобы параметры реально применялись в MLChat, после установки wheel 0.1.3 задать:

```powershell
$env:DIALOGUE_FACTORY = 'mlchat.integration:create_qwen35_9b_dialogue'
$env:LLM_BASE_URL = 'http://localhost:11434'
$env:LLM_MODEL = 'mlchat-qwen35-9b'
$env:LLM_RESPONSE_MODE = 'json_schema'
```

Перезапустить приложение. Фабрика использует тот же async interpret и native
LLMClient установленного backend. Представление клиента добавляет три поля
в JSON до его штатной сериализации. HTTP-соединения, авторизация, лимит ответа,
deadline, обработка ошибок и флаг used остаются у исходного клиента. Общий
HTTP-клиент и его event hooks не изменяются. Повторных генераций нет.
В фабрике хранится только неизменяемая конфигурация, пользовательского состояния нет.

PARAMETER think не поддерживается этой версией Ollama. Отключение выполняется
через [reasoning_effort в совместимом API](https://docs.ollama.com/api/openai-compatibility#v1chatcompletions).
Нативный ollama run не использует фабрику MLChat; для прямой проверки модели:

```powershell
ollama run mlchat-qwen35-9b --think=false
```

Это общий диалог с моделью, без интерпретатора и валидации MLChat. Сама модель
по /api/show по-прежнему сообщает thinking.default=true: выбранный режим
для MLChat определяется параметрами фактического HTTP-запроса.

Проверка фабрики с реальной моделью подтвердила temperature=0, top_p=0.8,
reasoning_effort="none", отсутствие reasoning в ответе и правильный AND-фильтр.
Затем выполнен отдельный полный прогон из 32 сценариев: пройдено 28,
медиана шага 1,953 с, максимум 4,860 с. Все 36 выполненных шагов уложились в 15 с.
В том отчёте отмечены провалы сравнения рейтинга выше 4, диапазона вместимости, ответа на AVG
и первой реплике «Покажи школы» в сценарии редактирования. Уточнение категории
в этом прогоне прошло. Это один прогон новой конфигурации, без подтверждения
сквозного GIS-поиска и без проверки устойчивости на повторениях.

Локальные отчёты: `.artifacts/mlchat-qwen35-9b-profile-smoke.json` и
`.artifacts/mlchat-evaluation-qwen35-9b-profile-ollama0407-0.1.2.json`.
Проверки с управляемой моделью: все прежние 80 тестов и 7 новых проверок профиля
прошли; новые тесты находятся в `integration_checks/test_generation_profile.py`.

Эти числа относятся к прежнему промпту. При диагностике диапазон вместимости
оказался ложным провалом оценки: `between` равнозначен паре `gte`/`lte`.
Актуальная проверка промпта 0.1.3 и новых формулировок —
в [протоколе качества](mlchat-quality.md).
С промптом 0.1.3 исходный набор пройден полностью в трёх прогонах:
32/32 каждый раз, медиана 1,891 с, максимум 5,640 с, все 111 шагов правильные.
Сравнение включает равнозначность `between` и пары включающих границ.
На отдельном наборе новых формулировок — 27/32; среди ошибок подмена OR на AND.
Свободный ввод пока не готов к приёмке; подробности и план исправлений — в протоколе.

## Контракт и состояние

Фабрика `mlchat.integration:create_dialogue` без аргументов возвращает stateless-объект:

```python
async def interpret(
    *, text, state_snapshot, capabilities, llm_client, deadline
) -> Candidate | Clarification | Unsupported: ...
```

Типы результата и фильтра импортируются из backend. Пример рабочего фильтра:

```json
{
  "schema_version": "1",
  "operation": "search_objects",
  "category": "school",
  "conditions": [
    {"field": "rating", "op": "gt", "value": 4},
    {"field": "capacity", "op": "gte", "value": 100}
  ]
}
```

Для количества по каждому району — `count_by_region`; сами результаты вычисляет backend.
Внутренний JSON-ответ LLM:

- `candidate`: `kind`, boolean `new_request`, `filter: FilterV1`;
- `clarification`: `kind`, `new_request`, русский `message`, `options`, `pending`;
- `unsupported`: `kind`, `new_request`, русский `message`.

`pending` содержит nullable `operation/category`, массив полных native-условий
`conditions` и непустой `missing` с недостающими параметрами. Незавершённые условия
не включаются в conditions. Например, для «школы с высоким рейтингом»:

```json
{
  "kind": "clarification",
  "new_request": true,
  "message": "Какой рейтинг нужен?",
  "options": [],
  "pending": {
    "operation": "search_objects",
    "category": "school",
    "conditions": [],
    "missing": ["Порог и сравнение для rating"]
  }
}
```

Схема генерируется из Pydantic-моделей и native FilterV1/Condition, без второго языка
фильтра. `proposed_state` модель не генерирует. MLChat собирает состояние версии 1:
исходный request_text, проверенный pending, вопрос и варианты. Условия проверяются
native-валидатором и capabilities; при неизвестной категории должна существовать
хотя бы одна допустимая категория, но она не подставляется до уточнения.
Размер состояния ограничен `state_bytes`. Неизвестные поля/версии отклоняются.

`new_request=false` — ответ на уточнение; прежние известные условия, категория и
операция обязаны сохраниться. Потеря ограничения — ошибка модели. `new_request=true`
заменяет pending самостоятельным запросом. Определение смысла/полноты перевода и
неподдерживаемых частей — задача модели: валидатор не доказывает соответствие
произвольному русскому тексту. Поэтому необходима приёмка с реальной моделью.

Продолжение с готовым Candidate должно разрешить хотя бы неизвестную категорию/операцию
или добавить условие: модель не может просто убрать missing и исполнить прежний
незавершённый фильтр. Отказ от прежнего ограничения требует самостоятельного запроса.

Точный Option.value либо однозначный label категории обрабатывается без LLM,
если в pending не хватает только category, а операция и все условия уже известны.
Применяется тот же FilterV1 и capabilities; при других недостающих параметрах поиск
не запускается. Для этого missing использует код category (принимаются также явно
перечисленные русские обозначения категории).

Входной snapshot не изменяется. Candidate предлагает `{}`, которое backend фиксирует
после успешного поиска. Unsupported продолжения сохраняет pending, самостоятельного
запроса — очищает. Завершённый фильтр/история в MLChat не сохраняются. Очистка и
изоляция вкладок, refresh, «Новый диалог», commit/rollback состояния принадлежат backend/UI.

До обращения к LLM отсеиваются явные команды редактирования без pending («оставь»,
«увеличь» и подобные), а также явно заданные пороги «с рейтингом ... число» вне
границ capabilities. Эти проверки только отказывают в неподдерживаемом запросе:
они не строят AST и не исправляют числа. При таком раннем отказе pending сохраняется.
Значения в кавычках и запросы по названию не рассматриваются как пороги рейтинга.

В модель передаются настоящие роли user/assistant: исходный запрос, предыдущий
уточняющий ответ с проверенными условиями, затем текущая реплика. Текущий ввод всегда
последний. Это устраняет воспроизведённое зацикливание на исходном «высоком рейтинге».
В компактной схеме убраны только аннотации title/discriminator, ограничения сохранены.

## Объём и ошибки

| Требование | Поведение | Проверка |
| --- | --- | --- |
| FR-3.1 | Пять категорий, native FilterV1 | КЗ-01 |
| FR-3.3.1–3.3.5 | eq, gt/gte/lt/lte, between, in, contains, boolean | КЗ-04–08 |
| FR-3.3.3, FR-3.3.6 | Точная дата, year, диапазон дат | КЗ-09–10 |
| FR-3.4 | AND | КЗ-12, КЗ-41 |
| FR-3.5.1 | Запрос count_by_region | КЗ-21 |
| FR-3.7, UC-03 | Уточнение, повторный вопрос, новый запрос | КЗ-03 |
| FR-3.8 | Схема, семантика, capabilities до Candidate | КЗ-33 |

Runtime-возможности задаются capabilities, без подмены старым статическим каталогом.
Ограничения эталонного backend: рейтинг-порог 1…5, остальные числовые пороги ≥0,
вместимость-порог только целый; даты eq/year/between/in. Пороги не округляются и не
обрезаются. Подстрока передаётся буквально, SQL-экранирование выполняет backend.

После MVP: геофильтры, OR/NOT над условиями, несколько категорий, относительные даты,
AVG/SUM/ранжирование, отбор районов по числу, NULL-предикат и редактирование выполненного
фильтра. Смешанный запрос требует Unsupported целиком. Эти отказы включены в приёмку.

Максимум один вызов LLM за шаг, без repair/retry и фоновых задач. Общий абсолютный
deadline задаёт backend (исходно 300 с); отмена распространяется. Коды ошибок:
`502 LLM_INVALID_RESPONSE`, `502 DIALOGUE_INVALID_RESPONSE` для несовместимого состояния,
`504 REQUEST_TIMEOUT`. Ошибки транспорта сохраняют код backend. В ошибки не включаются
значения модели. Пустой ответ LLM не является поиском с 0 результатов.


## Проверка после подключения

Через существующий чат проверить:

- «Покажи школы с рейтингом выше 4 и вместимостью не менее 100»:
  `search_objects`, `school`, два условия `gt/4` и `gte/100`.
- «Покажи школы с высоким рейтингом» → вопрос о пороге → «Выше четырёх»:
  `school`, `rating/gt/4`, очищенное состояние после успешного исполнения.
- «Сколько парков в каждом районе Томска?» → `count_by_region`, `park`.
- «Школы в радиусе 500 метров» → Unsupported без запуска поиска.
- Пустая выборка, сбой модели, новый диалог и независимые сессии:
  корректные ответы и изоляция состояния в backend/UI.

Ожидаемые ID и количества зависят от данных серверного стенда и задаются отдельно.
Проверки с имитацией LLM не подтверждают качество выбранной модели.
Тесты, локальные отчёты, инструменты оценки, прежний AST и геоданные остаются на
рабочем компьютере, исключены из Git и отсутствуют в новом клоне.
Для передачи тестировщику существующих материалов требуется отдельная поставка.
